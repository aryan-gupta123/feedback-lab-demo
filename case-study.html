ENGINEERING CASE STUDY / ACTUAL RECORDED FAILURE

A valid answer.
The wrong episode.

A chronological input contract had to be enforced before a feedback experiment could be interpreted.

THE CONTROL

Choose the best option in the newest completed episode.

In episode 9: cash 0, asset A −16,000, asset B −59,000. Cash is correct. An older episode 4 contains asset A +97,000. Values are integer microreturn units.

WHAT THE MODEL RETURNED

Asset A, +97,000.

The JSON was valid and mapped to a valid allocation. The model compared values across episodes and selected an old winner. A schema alone did not enforce the task.

Why this invalidated the next step

If stale feedback can override the intended latest episode, an apparent effect of feedback quality may actually reflect a context-selection error. This was an explicit numeric comprehension control, not a market prediction or a trading loss. The raw-history transfer gate passed only 4 of 6 cases, so that interface was stopped.

The fix: select by time before asking the model.

The latest-only preprocessor validates unique nonnegative episode numbers, then keeps the record with the largest episode number. It does not rank payoffs or choose an asset. The unchanged model and comparison prompt still select between cash and the two assets. The following excerpt illustrates the projection; it is not the full private implementation.

# Select chronology, never the best historical payoff.
latest = max(completed_episodes, key=lambda record: record["episode"])
# Send only latest to the model; it still chooses the action.
model_input = {"task": "past_feedback", "completed_episode": latest}

Regression checks reverse record order and change older payoffs while holding the latest episode fixed. The newest episode must remain unchanged. Duplicate or invalid episode numbers are rejected rather than guessed.

These are different development batteries, not a randomized before/after comparison. The result validates the narrower pipeline; it does not prove that the raw model learned chronology or that preprocessing generally improves reasoning.

A later content-hash review found one replay in the original v6 confirmation. All original observations were retained. A full additional 36-case battery was specified before inference and checked against all prior requests; it passed without changing the model, prompt, or scorer. The acceptance claim uses that fresh set. Seed separation alone had not guaranteed unique questions.

What this demonstrates

Separate output validity from task correctness. Make chronology a code-level invariant when the experiment requires latest-only context. Preserve failed cases and test whether evaluation inputs are truly new.

This case is selected to explain a failure mechanism, not to estimate failure frequency. Other failed iterations exist. The market pilot uses a related two-field action schema and selected-only past feedback; it has its own validation gates.
